---
title: routeup.json
description: The standalone config file for any project.
---

`routeup.json` lives in your project directory and gives routeup a default name
and port, so you can run `routeup serve` with no arguments. It works for any
language, use it whenever your project is not a Node project (for Node, you can
embed the same settings in [`package.json`](/docs/configuration/package-json-embed)).

## Minimal config

```json
{
  "name": "example-app",
  "port": 8080
}
```

With this present, run:

```bash
routeup serve
```

The configured name and port are used directly. A positional bare name is a
sub-route, so `routeup serve api` resolves to `api.example-app`.

## Fields

```txt
name     default project / route name used for bare-name resolution
port     the local port to proxy to
command  the shell command to run in script-runner mode (see the bare `routeup` command)
targets  optional list of path-routed targets for one-origin frontend + API setups
expose   optional public exposure settings, including paths
```

The `name` field doubles as the project name: a bare argument like
`routeup serve api` resolves to `api.example-app`, while a dotted argument is used
literally. See [Name resolution](/docs/configuration/name-resolution).

## Path routing

Use `targets` when one hostname should proxy different path prefixes to different local ports:

```json
{
  "name": "example-app",
  "targets": [
    { "path": "/", "port": 5173 },
    { "path": "/api", "port": 9080 }
  ]
}
```

This keeps the browser on one origin, for example `https://example-app.localhost/api/users`, while routeup sends `/api/*` to the API port.

## Path-limited exposure

By default, `--public` exposes every path on the route. Limit public exposure with `expose.paths`:

```json
{
  "name": "example-app",
  "port": 8080,
  "expose": {
    "paths": ["/api/webhooks/*"]
  }
}
```

The route still works locally at every path, but only matching paths are reachable through the public URL.

## Request and response capture

routeup can retain request and response data so you can inspect it later with
`routeup inspect <request-id>`. Capture is off by default because retained data
may contain secrets.

```json
{
  "name": "example-app",
  "port": 8080,
  "capture": {
    "request": true,
    "response": true,
    "redact_headers": ["authorization", "cookie"]
  }
}
```

| Field | Description |
|---|---|
| `request` | Retain incoming request headers and body |
| `response` | Retain upstream response headers and body |
| `redact_headers` | Headers to omit from capture (case-insensitive); they are still forwarded to the upstream |

Each captured message is bounded to 256 KiB. If a body exceeds that, `routeup inspect`
shows a partial prefix and marks the capture as incomplete.

Get the request id from `routeup logs`, then inspect it:

```bash
routeup logs example-app --follow
# 12:41:03 public example-app POST /api/webhooks/github 200 38ms req_abc123

routeup inspect req_abc123
```

## Request capture

Enable `capture` to retain incoming request and outgoing response data so
`routeup inspect` can show the full headers and body later:

```json
{
  "name": "myapp",
  "port": 8080,
  "capture": {
    "request": true,
    "response": true,
    "redact_headers": ["authorization", "cookie"]
  }
}
```

`request` and `response` are independent — enable only the direction you need.
`redact_headers` removes those header values from the stored copy before
`routeup inspect` can see them; the upstream service still receives the
originals untouched.

Captured data is kept in an in-memory ring buffer (last 200 requests) and
cleared when the agent restarts. Each message is capped at 256 KiB.

See [`routeup inspect`](/docs/cli-reference/inspect) and
[`routeup logs`](/docs/cli-reference/logs).

## Discovery

routeup looks for config in the **current working directory only**: there is no
walk-up to parent directories. If both `routeup.json` and a `package.json`
`routeup` block exist in the same directory, `routeup.json` wins.

Per-language manifests beyond `package.json` (such as `pyproject.toml` or
`Cargo.toml`) are not read; non-JS projects use `routeup.json` directly.
